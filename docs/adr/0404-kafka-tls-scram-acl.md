# 0404. Kafka clients authenticate with SCRAM-SHA-512 over TLS, one KafkaUser per role

- Status: Accepted
- Date: 2026-10-09
- Lane: sf-data

## Context

Red-team finding 7: Kafka without authentication lets any pod read customer data or inject events. Several
components use Kafka with very different needs: the Debezium source (write change events), the Iceberg sink (read
change events, its own control topic and transactions), Flink (read), a lag exporter (describe only).

## Decision

- One listener, `tls` on 9093: TLS + `scram-sha-512`; no plaintext listener. `authorization: simple`;
  `auto.create.topics.enable=false` so every topic is declared.
- KafkaUsers (`deploy/platform/kafka/base/users.yaml`), passwords generated by the User Operator into Secrets:
  `debezium` (Connect worker group + internal topics, write `shop.*` and the heartbeat topic), `iceberg-sink`
  (read `shop.public.*`, read/write `iceberg-control-*`, groups `connect-iceberg-sink*`, transactional ids
  `iceberg-sink-*`), `flink` (read `shop.public.*`, groups `flink-*`), `kafka-exporter` (describe).
- One Kafka Connect cluster (`cdc`) whose worker identity is `debezium`. The Iceberg sink switches its clients to
  `iceberg-sink` with `consumer.override.sasl.jaas.config` and `iceberg.kafka.*`; the worker allows only that
  (`connector.client.config.override.policy=Principal`). Credentials reach connectors through the Strimzi
  `KubernetesSecretConfigProvider` (`${secrets:ns/name:key}`), granted per Secret name.
- The sink's own control-topic clients get every security setting explicitly: they load the worker properties
  file, whose values are unresolved provider placeholders (Strimzi writes `${strimzisecrets:…}`).

## Alternatives considered

| Option | Why not |
|---|---|
| mTLS client certificates | Fine for Strimzi clients, awkward for Flink SQL and future Python clients; SCRAM passwords fit Secrets/ESO |
| Two Connect clusters (one per identity) | ~1GB more memory for the same isolation the override policy gives |
| Plaintext inside the cluster + NetworkPolicy | No identity, no ACLs; a NetworkPolicy mistake exposes everything |

## Consequences

- Positive: a client without a KafkaUser is rejected; each component can only touch its topics/groups.
- Negative / risks: the transactional and group prefixes of the Iceberg sink are implementation details
  (checked in Iceberg 1.12 source: `Channel`, `Worker`, `Coordinator`); a sink upgrade can change them.
- When to revisit: Iceberg sink renames its groups/transactional ids, or Flink needs write access.
