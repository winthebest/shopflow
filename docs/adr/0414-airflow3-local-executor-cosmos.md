# 0414. Airflow 3 with LocalExecutor, dbt through Cosmos, DAGs baked into one image

- Status: Accepted
- Date: 2026-10-09
- Lane: sf-data

## Context

Phase 5 schedules dbt every hour, Iceberg maintenance and an exact reconciliation every day, on a laptop-sized k3d
cluster and on short-lived EKS sessions. Task failures must alert, and the metadata database (CNPG) is restored
from backups on AWS, so its encryption keys must be fixed, not generated by the chart.

## Decision

- **Airflow 3** (official chart, `executor: LocalExecutor` in both environments): tasks run as subprocesses of the
  scheduler, no Redis, no workers, no pod per task.
- **Image `shopflow-airflow`** (`data/airflow/Dockerfile`, published by `data-images.yml`, pinned by digest):
  - the slim Airflow 3.3.2 image plus only `postgres`, `fab` and Cosmos, under Airflow's release constraints;
  - dbt in its own virtualenv from `data/dbt/uv.lock`, so dbt's pins never fight Airflow's;
  - the dbt project with a manifest parsed at image build;
  - the DAGs (`data/airflow/dags`).
  DAGs and the dbt project they run change together and ship as one tested artifact; there is no git-sync.
- **dbt through Cosmos 1.15** (`dbt_build`): the task graph is rendered from the baked manifest, so DAG parsing runs
  no dbt. Each silver/gold model gets a run task and a test task. Tests with several parents (relationships) run
  after all of them, and ephemeral staging models are not tasks. A guard task fails the run when no CDC epoch has
  completed.
- **Plain dbt commands** (BashOperator) for the rest:
  - source freshness;
  - reconciliation (`dbt test --select tag:reconciliation --vars '{reconcile: true}'`; those tests are disabled
    otherwise, so Cosmos never renders them);
  - Iceberg maintenance (`dbt run-operation iceberg_maintenance`: optimize, optimize_manifests, expire_snapshots,
    remove_orphan_files at the 7-day floor).
  One Trino identity (`dbt`) and one profile serve all of them.

Verified offline on 2026-10-09: the image ran the three DAGs with `airflow dags test` against the Kafka Connect smoke
stack plus Trino 483.
- `dbt_build` succeeded with no retries.
- `iceberg_maintenance` maintained 16 tables (bronze `orders` compacted to one file).
- `reconciliation` passed; it failed on a fake row added to silver.
- A Postgres change made after the last silver commit is skipped as expected staleness.
- `data-ci` imports every DAG inside the image and checks DAG ids, schedules, tasks and graph (`make data-airflow-check`).

## Alternatives considered

| Option | Why not |
|---|---|
| Dagster | Asset model fits dbt well, but the plan targets Airflow, the more common orchestrator in data-platform jobs |
| KubernetesExecutor | A pod per task: slow starts and memory churn on a laptop; Optional later |
| CeleryExecutor | Redis and worker pods for a handful of hourly tasks |
| Full `apache/airflow` image | Dozens of unused providers; Trivy finds fixable CRITICAL CVEs in them (and in Airflow 3.2.2) |
| dbt installed into Airflow's environment | Its dependency pins conflict with Airflow's constraints |
| git-sync for DAGs | DAGs would move independently of the dbt project and dbt version they call |
| Trino provider for maintenance | A second connection configuration for the same user and catalog |

## Consequences

- Positive: one immutable, scanned artifact per change; dbt lineage visible as Airflow tasks; no extra services.
- Negative / risks:
  - Any DAG or dbt change needs an image publish and a digest bump.
  - LocalExecutor runs tasks inside the scheduler pod, so it is sized for the parallel dbt processes.
  - Every k3d cluster is new, so Airflow sees every DAG for the first time; `core.dags_are_paused_at_creation` is
    False (#175), otherwise nothing runs until someone unpauses it.
  - The chart comes from an index in this repo (`deploy/platform/airflow/helm-repo`, #173/#174) that points at
    dlcdn.apache.org: the official index points at archive.apache.org, which the local network cannot reach.
    dlcdn keeps only current releases, so a chart bump needs that index updated too.
- Verified on the cluster (batch slot, 2026-10-10, `core,obs-lite,data,batch`, k3d):
  - Chart 1.22.0 runs Airflow 3.3.2 (migrations, create-user, scheduler, dag-processor, api-server).
  - `dbt_build` on Trino: 28/28 tasks, 5m42s for the first run on empty schemas, 44-46 s for later runs.
  - After 601 k6 checkouts, gold matches Postgres exactly. `fct_orders` 601 = `orders` 601; by status, paid 589
    and failed 12 on both sides; paid revenue 52,844.70 on both sides. `mart_daily_revenue` is consistent and
    `dim_customers` holds 100 rows. Three test orders inserted, updated and deleted in bronze are absent from
    silver and gold, as intended.
  - Every gold table's `$snapshots` shows `append` (dbt's CREATE OR REPLACE), which the freshness exporter
    counts; `data_refresh_age_seconds` has a series for each of the 5 gold tables.
  - Not yet measured on a cluster: the gold-freshness SLO, which counts only after namespace `airflow` is 2 hours
    old. So far only its promtool tests cover it; a slot that keeps the cluster up for more than 2 hours (Gate 3,
    game day A) will measure it.
  - RAM: server 7.84 GB + agent 4.55 GB, about 12.4 GB; namespace `airflow` 0.85 GB. That is above the 11 GB
    budget for shared slots, so `batch` runs as an exclusive slot, like `rt`.
- When to revisit: tasks need isolation or more parallelism than one scheduler pod gives (KubernetesExecutor), or
  Cosmos breaks on an Airflow upgrade (fall back to `dbt build` in one BashOperator).
