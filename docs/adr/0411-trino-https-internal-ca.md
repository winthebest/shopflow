# 0411. Trino HTTPS with a certificate from the internal cert-manager CA

- Status: Accepted
- Date: 2026-10-09
- Lane: sf-data

## Context

Trino accepts password authentication only over HTTPS. Clients are in-cluster (dbt, Metabase, the exporter, the
bronze DDL Job) plus port-forwarded tools; no public endpoint (UIs only through port-forward, plan security
baseline). Trino reads its key and certificate chain from a single PEM file.

## Decision

A cert-manager `Certificate` `trino-tls` in `lakehouse`, issued by the cluster's internal CA `ClusterIssuer`
(sf-platform), DNS names `trino`, `trino.lakehouse`, `trino.lakehouse.svc`, `trino.lakehouse.svc.cluster.local`,
ECDSA P-256, `rotationPolicy: Always`, with `additionalOutputFormats: CombinedPEM` (key `tls-combined.pem`, beta in
cert-manager 1.15, GA in 1.18). Trino listens on 8443 with that file; the HTTP port stays for health checks and
internal communication (shared secret). Clients trust the CA through the `ca.crt` key of the same Secret.

## Alternatives considered

| Option | Why not |
|---|---|
| Self-signed certificate generated by an init container | Rotation and trust distribution by hand |
| TLS terminated at Envoy Gateway | Trino must not be exposed through the shop Gateway; in-cluster clients would still talk plain HTTP |
| Let's Encrypt | Needs a public domain; internal service names cannot be validated |

## Consequences

- Positive: passwords never cross the network in clear text; certificates rotate automatically.
- Negative / risks: depends on the internal CA issuer name from sf-platform; clients must mount `ca.crt`.
- When to revisit: a service mesh with mTLS is introduced.
